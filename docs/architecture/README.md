# Architecture

This is the canonical current architecture. Historical architecture URLs redirect here. The app is macOS-only and targets Xiaomi Smart Band 9; physical verification currently covers the NFC model.

```text
Desktop UI → bridge → Tauri commands → application services → private files
                                               ↓ JSON Lines
AI Hooks → loopback HTTP → Node runtime core → transport adapter
Mac sampling ────────────────────┘                    ↓ JSON Lines
                                   Rust SPP/Core transport → Buddy controller
                                                         ← v1 application ACK
```

## Ownership and dependency direction

| Component | Owns | Boundary |
|---|---|---|
| Desktop | Official login window, preferences, selected device, tray/window lifetime | Typed application operations; no credentials in UI responses |
| Runtime core | Connection intent, retry, snapshot delivery, install/wake coordination | Injected clock, scheduler, sampler, transport and identifiers |
| Runtime adapters | OS metrics, loopback HTTP, child process I/O and checkout paths | No reconnect/wake policy |
| Native transport | Fixed upstream Core/SPP, authentication and device operations | JSON Lines, fixed sanitized diagnostic codes |
| Band controller | Snapshot consumption, settings receipts, foreground lifetime and rendering state | Injected Vela APIs and timers |
| Shared modules | v1 validation/ACK matching and existing display/animation calculations | Pure ES5 CommonJS; no platform imports |

Entrypoints compose these parts. Desktop domain/wire models have no platform effects; application operations are shared by tray/window adapters. The credential model retains the vendored account token data type to preserve its persisted format. Vendor and pinned upstream internals remain isolated.

Desktop frontend modules use only `bridge.js` for Tauri calls. Preview rendering consumes the same canonical presentation functions as the band; it reconstructs artwork, not a device screen capture. Mac appearance, band theme and activity state remain independent. Interface text is localized in the desktop frontend (`i18n.js`, `locales.js`: Simplified Chinese, Traditional Chinese, English). Catalog keys are the Traditional Chinese source strings, so runtime and Rust messages are translated at display time without changing the wire contracts. The tray menu and login window title use the same saved `language` preference (`system` by default).

## Contracts and delivery

The desktop/runtime and runtime/transport channels are private inherited stdio with one JSON object per line. Credentials appear only in the necessary connect/initial frames and never in state/health projections. Known commands are typed/validated at boundaries; additive ACK/runtime fields are retained. Synthetic examples shared by JavaScript and Rust live in `packages/buddy-shared/fixtures/v1.json`.

Snapshot protocol v1 keeps `session`, `seq`, CPU/memory/disk, activity mode, `buddyTheme`, `settingsRevision` and `keepScreen`, plus the optional additive `page`. A matching ACK must identify the current session/sequence and a valid receipt. Theme success additionally requires the matching revision/theme and `settingsApplied=true`; queued or failed storage never counts as durable confirmation. The package ID remains `com.macprobe.band9`.

There is one selected device, one transport child and at most one unacknowledged snapshot. Sampling is sequential, approximately every two seconds; new samples replace unsent older data. Connection recovery backs off to 30 seconds and stops after eight retries. Authentication rejection and competing-client conflicts require user action. Disconnect removes reconnect intent. Installation suspends snapshots and waits for a bounded device result.

Missing application ACK enters standby with approximately 30-second probes. A separate device-status check distinguishes sleeping Buddy from link failure. Transport generation checks reject events from abandoned children; pause/disconnect/install clear pending wakes. Stop cancels owned timers and ends workers.

## Activity and bounded wake

Hooks carry only event, hashed session identifier and timestamp. The receiver binds `127.0.0.1:10731`, rejects browser-origin writes, and bounds input. Codex compatibility paths remain supported; Claude Code and custom harness senders namespace session hashes by provider. The [project skill](../../skills/buddy-hooks/SKILL.md) and merge-only installer provide project-scoped setup ([ADR-004](ADR-004-local-agent-hooks.md)). Hook failure exits successfully and never makes a tool permission decision. State is bounded to 128 sessions and not persisted. Independent main sessions aggregate with attention before working before thinking; one completion cannot hide another active session. Counts do not infer parallel tool calls or subagent tasks. After 15 minutes without an event, a session displays a stale warning but remains active; with activity keep-awake enabled, it keeps renewing the display: silence cannot establish that a long task finished. The explicit `reset_activity` operation clears observed activity without cancelling the AI host's work, including a cancelled Claude task whose host did not send a terminal event.

UserPromptSubmit, a new PermissionRequest, and task completion can request wake. Ordinary metrics/tool traffic cannot. One pending event is retained with a 60-second TTL and a 10-second global launch cooldown; attention takes priority. Cancellation/tool resumption invalidates obsolete pending work.

Desktop band actions (theme, page, wake, display timeout, activity keep-awake, power saving, task reset and version check) are user operations ([ADR-002](ADR-002-user-operation-wake.md)). They are accepted while the link is connected, waiting or in standby. Each one replaces queued event work, bypasses the event cooldown, preempts an in-flight event wake, and launches Buddy with a fresh display lease. Runtime state carries one `operation` that settles once (`done`, `failed` or `cancelled`) after a matching display lease plus the operation-specific settings/page/inventory receipt. Launch enqueueing alone only advances to applying. Launch failure, a 25-second bound, link loss, disconnect and installation also settle it. Background pause still permits an explicit operation and stops snapshots again when it completes; those paused snapshots never renew active-task holds. The optional snapshot `page` is sent only during a page operation. The desktop UI shows progress on the acting control and reports each result in a fixed toast.

An early application ACK without an active display lease does not immediately fail a wake: fresh-sequence snapshots retain the same wake ID until the original 15-second wake deadline. No extra launch or deadline extension is allowed. A later confirmed lease completes the operation; explicit brightness errors still fail immediately, and late receipts cannot revive cancelled or expired operations.

Explicit connection/startup requests one initial launch; background reconnect does not synthesize another. Native launch checks the installed app list first. Missing Buddy requests installation; successful installation starts a separately tracked post-install wake/ACK phase, including when background synchronization is off.

The `syncEnabled` desktop preference defaults to true and is shared by the window switch and tray pause action. Startup restores the saved pause command before auto-connect, so disabled sync cannot launch Buddy or send snapshots during restart. Every explicit manual Buddy action requests one wake on a ready link, including either direction and repeated values of a setting. Background pause does not block these bounded transactions. Resuming synchronization also wakes once when keep-awake is enabled and an observed task is active. These are user actions, never periodic relaunches. All desktop preference mutations and saves share the session mutex on a blocking pool, so delayed appearance snapshots cannot overwrite a newer band choice.

Persistent `keepScreen` stays false. The separate `activityKeepAwake` preference defaults to false; changing it saves locally and configures the runtime immediately. Event and manual wakes remain bounded while it is disabled. Each accepted wake sends a unique ID with a band-local display lease. The lease uses the saved hold (default 20 seconds, 5–1800) clamped to the ACK's `capabilities.maxWakeHoldMs`, or 30 seconds when Buddy advertises none ([ADR-003](ADR-003-band-capabilities.md)). Duplicate wake IDs cannot extend it. Buddy 0.5.4 advertises `activityHold`: when the preference is enabled, increasing-sequence snapshots can then renew a 15-second local activity watchdog while a confirmed session is thinking, working or awaiting approval. The final terminal event, or disabling activity keep-awake, starts the saved idle grace once; ordinary idle snapshots never slide the deadline. Missing synchronization expires locally, and hide/exit cancels every lease. Optional `sessionCounts` adds one color segment per concurrent active session to the existing main ring, capped at six, without count text or AI-provider identity and independently of the selected theme. Legacy Buddy receives its original fields and one-shot lease ([ADR-005](ADR-005-active-display.md)). Launch confirmation requires a matching application ACK, lease ID/remaining time and accepted keep-screen request. Firmware controls actual illumination/sleep; ACK is not physical measurement. See the [verification guide](../testing.md).

Buddy ACKs advertise `capabilities` (maximum lease, themes, page and power-saving support). Themes beyond ChatGPT and Claude are applied only when advertised, because older Buddy rejects whole snapshots with unknown enum values. The optional `powerSaving` field is sent only to supported Buddy versions; it defaults off and is persisted on both devices. Character/resource animation targets 30 updates per second normally and five in power-saving mode, with image-source animation across every live state. The desktop preview uses bounded image caching and stops while hidden. Aggregate task counts appear as up to six colored segments within the original main ring, with exact counts kept outside the capsule on the desktop ([ADR-008](ADR-008-animation-and-task-rings.md)). After authentication, every five minutes and on manual refresh, the runtime asks the transport for `device_status`. It exposes the firmware, model, battery, charging and storage values as non-persisted `state.device`; serial number and IMEI are never forwarded.

Buddy installation management is confined to the desktop's band page. `state.buddy` distinguishes unknown/checking inventory, absence, installed versions, an available bundled update, a matching version and a newer device version. Native app inventory exposes only Buddy's presence and numeric version code; missing ACKs never establish absence. Initial/post-install launch reuses its existing app-list request; paused startup and background reconnections use bounded read-only queries. Explicit `check_buddy` carries a request ID, wakes Buddy first and checks inventory after a display receipt; confirmed package absence completes the check without an impossible app wake. The available version comes from metadata bound by SHA-256 to the actual bundled RPK. A fresh matching ACK whose version name exactly equals that bundled version can confirm `current` despite an older cached inventory code; it never supplies or infers a numeric code. Repeated unchanged inventory preserves that confirmation, while changed inventory invalidates old version evidence and newer numeric builds remain `newer`. Transfer completion alone is not an installation receipt: a missing final receipt remains an unconfirmed operation even when a later ACK independently confirms the running version. Installation/check failures remain in the band-management state, not a global update banner ([ADR-007](ADR-007-band-installation-state.md)).

## Build and compatibility

`scripts/prepare_shared.py` stages canonical shared source for Vela and wraps unchanged CommonJS source for browser ESM. It never rewrites export strings. App-local copies and artwork are generated build outputs; `scripts/render_band_ui.py` remains the geometric band artwork source. Desktop branding uses the approved master `apps/desktop/artwork/app-icon.png`; `scripts/prepare_desktop.py` generates its app/UI sizes and the monochrome menu-bar template.

The desktop bundle carries Node, runtime/shared source, native transport and its Buddy RPK/metadata under `Contents/Resources/runtime`; direct Cargo development runs retain checkout-path fallback. Explicit GitHub update checks/downloads and verified staged installation belong to the desktop updater ([ADR-006](ADR-006-desktop-updates.md)), independently of device state. `mac/codex-hook.mjs` and `mac/buddy-runtime.mjs` retain old executable paths. Data location, preferences, Hook endpoint, package identity and public npm commands are unchanged. Rust packages and Quick App dependencies stay independently locked; no workspace manager or runtime rewrite is introduced.
