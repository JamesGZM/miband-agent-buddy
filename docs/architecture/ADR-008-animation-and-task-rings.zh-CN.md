# ADR-008: 代码绘制 Buddy 动画与任务环

[English](ADR-008-animation-and-task-rings.md) · **简体中文** · [繁體中文](ADR-008-animation-and-task-rings.zh-TW.md)

## 问题

位图动画帧使本地传输过大。原生绘图实验验证了组件能力，但诊断画面没有保持已确认的 Buddy 设计。

## 决策

手环界面优先使用代码绘制并保留已确认设计。图片例外、源码职责及验证流程见[快应用界面指南](../development/quickapp-ui.zh-CN.md)。

当前帧率设置为 `buddyFps` 整数 10–30，默认 10；省电模式固定 10，并保留关闭后恢复的选择。所有边界验证范围，运行时仅向声明能力的 Buddy 发送，持久化回执匹配后才确认完成。预览使用同一原生几何、有效帧率与新鲜 ACK 的动画时间；回报目标帧率不等于实测面板刷新率。照片中直线也出现双线，因此将底轨隔离到固定背景 stack，防止新增子节点覆盖进度线；用户报告 code.7 已有改善，但这不能证明唯一的固件根因。

正式页面使用原生 div 矩形及弧形 progress 绘制原来的 490×192 布局。`packages/buddy-shared/presentation/geometry.js` 统一定义三个角色、七像素胶囊外框、状态颜色、加载高光、并行任务等分色段及三层资源胶囊。桌面 canvas 使用同一份几何。资源标签与数字保留原布局。

保留 32 级呼吸、96 个加载位置、17 个中心位置及原周期；手环和桌面预览共用 10–30 FPS 目标，默认 10，省电固定 10，不代表实测面板帧率。资源页静止后仅保留过期计时；隐藏、销毁和停止均取消所属工作。

生成器删除已知的废弃 capsule 输出目录，不再生成图片帧。桌面只留三个主题缩略图；手环包只有入口图标一张图片。图标由确认的桌面母图生成，192 像素资源内保留 160 像素图形。普通及本地构建都审核包内图片。本地构建器仅附加测试版本并备份旧包，不再替换 UI。

## 资源页后续

后续照片显示双线已有改善，但 CPU 弧线更新会留下累积缺口。根因尚未确认。图形现改为先把共享横向几何投影到手环纵向坐标，再绑定原生组件，取消图形父容器的旋转；文字保留原方向。测试验证投影的坐标、角度、进度及角色缓存。在 Smart Band 9 NFC 固件 3.1.32 的 code.8 短时检查中，用户确认方向正常、CPU 数值变化时缺口未再出现。这仅证明短时视觉改善，不代表长期稳定、面板帧率已测得或原来的熄屏／断线已解决。帧率改为与秒数相同的数字输入、保存按钮及 Enter 提交，范围仍为 10–30，省电固定 10。

此前用户认可角色页，但资源接点仍异常。原生资源路径改为固定直线与半圆，只在实际路径端点加圆帽；弧形几何固定，仅更新进度。两像素底轨与六像素填充共用中心线，0–100% 保持固定 ID 和数组长度。相同显示值跳过几何生成，ACK 与文字仍更新；数字节点仅在资源页创建。测试覆盖这些约束；短时视觉结果见上，设备 heap／CPU 收益尚未测量。

## 替代方案

保留废弃帧浪费传输时间；假设 Canvas 缺少固件证据；独立诊断角色改变已确认设计。采用已在设备确认的原生组件和共享纯几何保留现有 UI。

## 兼容性与证据

v1 协议、包标识、偏好、手势和亮屏租约不变。singleTask 页面独立管理控制器、通道和计时器；可选生命周期、绘图及脱敏传输回执区分页面隐藏、ACK 缺失和进程退出。

用户在 Smart Band 9 NFC 固件 3.1.32 确认原生几何、圆弧动画及新图标。查询 API 缺失表示未知。三次远程前台启动保持一个活动页面；刻意注入的传输 SIGTERM 自动恢复。主动检查应用列表期间的 ACK 间隙不证明自发蓝牙故障。原来的偶发熄屏／断线根因仍未确认；用户最新明确表示目前未熄屏。

测试覆盖几何边界、精确胶囊色段长度、所有主题状态、姿态数量、插值、正常／省电节奏、重复刷新、清理及两端生成模块一致性。构建与 ACK 不证明实机还原度、持续亮屏或电量表现。未获授权发版。

## 实机失败与有界原生更新

用户报告 code.3 卡死并令手环重启，此版实机验证失败。此前 ACK 与单元测试不代表稳定。报告前的诊断显示资源页、Buddy ACK 超时、传输进程退出为零，不能据此确定固件崩溃根因。

旧原型缓存角色矩形，只以 10 Hz 改少量数值并使用一个弧形组件。code.3 以 30 Hz 替换两个观察数组，工作角色页最多八个弧形，典型资源页九个。这违反官方[原地更新页面对象](https://iot.mi.com/vela/quickapp/zh/guide/best-practice/memory.html)及[减少动态样式和重绘](https://iot.mi.com/vela/quickapp/zh/guide/best-practice/business.html)的建议；渲染及观察器压力是有依据的假设，尚无崩溃堆栈证明。

修正保持观察数组及稳定色段 ID，仅写变化字段；角色几何缓存、整体位移；完整胶囊用单一边框。当前目标默认 10 FPS，可选 10–30，省电固定 10；只有局部笔划使用圆弧，单任务工作角色最多四个。资源插值与亮屏租约不变。测试覆盖十五分钟模拟动画不替换数组及一百次切页；固件内存、持续表现及不再重启仍需耐久实测。

code.4 连续三分钟的 19 次采样保持同一页面启动标记、ACK 持续且无超时；用户报告两页曲线与直线接点异常。原生修正将中心线几何转换为 LVGL 外缘半径，并将笔划边界与中心统一到整数像素。接点剖面测试先失败后通过，检查角色及资源线宽在两个切点的内外边界。公开 QuickApp 核心为预编译库，因此 LVGL 源码支持半径假设，但不证明 Band 9 私有适配实现；实机视觉仍待确认。

## 静态底圈与原生绘制验证

任务聚合与有序配色仍由 App 负责。Buddy 0.5.11 虽降低了模型更新量，实机多任务测试仍发生重启，因此该方案本身不能视为已解决。

后续本地候选版将不变底圈与高光分开绑定。底圈使用官方 `style.static`；配色或页面改变时用新的 `tid` 重建，动画不修改底圈列表。动态元件每次提交完整样式，避免逐字段触发样式表达式；保留弧线原有底色；0.5.12 强制透明后用户报告外圈变形，0.5.13 撤回这项视觉改动。用户仍报告顶部直线偏细、接点异常；下一候选版将原生笔划统一为偶数像素，角色外圈和高光为 8 像素，使中心线与线帽半径均落在整数像素，资源笔划仍为 6 像素。共用原生预览同步采用该几何，接点测试新增中心线和线帽检查；此假设仍需实机确认。角色容器缩至图形实际边界，绝对坐标和原版动画保持一致，避免移动全屏透明容器。页面持有自己的角色数据副本，不增加图片、蓝牙动画帧或降低设置帧率。

回归检查覆盖静态节点更新、同值快照、完整样式坐标、角色坐标与边界和生命周期。1–6 色的 80 帧模型量测均为 520 次动态字段写入、底圈写入与元件替换为零；编译产物确认包含静态样式标记。这些不是原生内存、重绘区域或屏幕帧率量测，也不能证明重启原因；候选版仍需实机确认。参见[官方内存优化](https://iot.mi.com/vela/quickapp/zh/guide/best-practice/memory.html)。官方组件目录不能证明该手环支持 Canvas，禁止直接假设网页 Canvas API 可用。

实机跟进：用户仍报告 0.5.14 顶部直线与曲线交接异常，偶数线宽未解决该缺陷。当前仅为未通过外观验收的本地候选版；继续调整几何前需要当前实机清晰照片作对照，不能将底色透明或奇数线宽当作已证实原因。

0.5.15 本地量测版保持这些外观参数，使用官方 `getBoundingClientRect` 在布局完成后比较画布与元件的请求／实际边界，只在静态节点更换或返回页面时读取。1 秒期限及代次检查处理无回覆或迟到回覆，隐藏和销毁时取消定时器。既有 ACK 诊断最多携带三个有界数值矩形及枚举状态，桌面健康记录使用白名单。边界不能证明光栅化线宽、半径语义或重启原因；不采集截图、提示词或设备标识。

实机 0.5.15 读回的画布 192×490、直线 8×157、弧线元件 186×186 及位置均与请求相符。参考像素测试另重现绘制顺序缺陷：统一先画直线后画弧线，使主笔划弧线覆盖接点的亮色尖端，静态弧线也可能盖住动态直线。0.5.16 将底圈、主笔划、尖端分为 0／1／2 层，整层顺序绘制；手环仅分组已有元件，Mac 预览同步，不改几何参数和帧率。测试检查思考／工作动画、上下接点、1–6 色、模板顺序及原地更新。软件不透明内部像素通过，不代表固件抗锯齿或实机稳定性已通过；仍需实机确认。三项量测可用时也读取完整胶囊边界，以核对不同元件的边框尺寸。


## 0.5.16 失败后的完整边框能力验证

0.5.16 实机仍重启，用户明确指出外层曲线错误；布局边界相符及尖端绘制顺序测试不能证明实际轮廓或稳定性。独立本地 `--capsule-border` 模板把两个完整原生胶囊边框放入固定尺寸、关闭双向滚动的视窗，仅取 App 编译的前两个真实任务颜色。通过依赖注入暂停角色动画，保留原控制器、过期／完成期限、连线及亮屏租约；正式入口不变，动画默认开启，预览跟随 `animationEnabled=false` 回执暂停。此实验替代继续猜线宽或半径。建置器才会选择模板、重定位其可检查的源导入，并仅提高临时包的 API level 2 与本地补丁版本，既有命令兼容。诊断仅允许枚举与数值。编译及 365 项软件测试不能证明本固件会正确裁切越界子元件；必须确认两段不同颜色及连续外曲线，才考虑采用这个后端。本控制版不验证最终动画、六色或长期稳定性。不增加启动图示外的图片、虚构任务事件、设置迁移或发布。

```sh
python3 scripts/build_band_probe.py --capsule-border --revision 1 --activate
npm run build:desktop -- --release --signing-mode local
```

启用时保留旧 RPK／元数据备份；之后运行 `npm run build` 会恢复正式源码包，打包本控制版时请保留已启用的原型包。


## 控制实验后恢复完整边框的 Loading 与呼吸

用户反馈 0.5.17 静态控制版的线条目测正常，并要求恢复呼吸与 Loading。这只提供完整外轮廓的视觉证据，尚未确认双色裁切与长时间稳定性。Buddy 0.5.18 的角色页使用完整原生边框，由共享代码生成矩形 scroll 视窗，划分主机准备的 1–6 种颜色。一个 RGBA 黑色边框统一调制呼吸，不逐个更新任务颜色。两个固定 Loading 主体和两个亮端各用两个裁切视窗，节点结构与每帧模型写入量不随任务数增加。各子边框始终是竖屏 184×482、宽 8 像素的完整胶囊。资源页、连接和亮屏租约保持原逻辑。

恢复分段 progress 弧线会重新使用尚未通过实机验收的轮廓实现；逐颜色呼吸则会让响应式更新量随任务数增长。共享几何为手环和有新鲜回执的 App 预览提供相同视窗、呼吸相位、角色姿态和 Loading 颜色。此实现需要官方 API Level 2 的 scroll 组件；包身份、偏好和协议 v1 保持兼容。RPK 仍仅含启动图标一张图片。测试覆盖边框像素完整且不重叠、固定 Loading 节点、坐标投影、呼吸、与任务数无关的模型更新、销毁和预览重建。这些模型断言不代表固件内存/CPU 测量、真实裁切/栅格正确或已解决重启；实机动画与耐久验收仍待完成，不发布。


实机跟进：用户反馈恢复后的效果可以，正在运行两个真实任务，暂未出现卡死或重启。App 预览也显示了双色外圈和 Loading。这只是初步短时间验证，不代表耐久测试通过或已验证六任务稳定性。
